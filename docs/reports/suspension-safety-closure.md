# P0 suspension safety closure and provider contracts

## Decision

**BLOCKED for production.** The PulseOS admission changes close the checked database race for Runo, CCS IVR, Meta WhatsApp inbound and WhatsNexus inbound. The companion WhatsNexus source exposes a separate acknowledged-loss path. Production retry, provider send isolation and an approved patient enquiry fallback still require evidence.

## Meta holding and platform visibility

- **VERIFIED in source.** Migration 0053 stores bounded provider IDs and timestamps only. The unique connector/lead key is checked under tenant serialization. The per-tenant cap is 1,000 unexpired references and processed markers. Request bounds are 256 KiB and 50 references. Retention is seven days. Cleanup deletes up to 500 expired rows per tick and skips locked rows.
- **VERIFIED in source.** Replay requires the platform restore permission, explicit approval and the current active lifecycle version. It processes up to five due entries, with a maximum of three attempts and one-/two-minute delays before subsequent attempts. It rechecks version, ownership, Page and current credential configuration before ingestion. A completed reference is cleared while its marker is retained. Audit events expose actor, tenant, action and result without patient data or credential values.
- **FIXED.** Both active and replay Graph lookups run outside DB locks. Rechecking the exact reference and current config/credentials prevents applying stale fetch results. If suspension wins during active fetch, admission can still hold the reference. Concurrent replay requests can issue duplicate read-only Graph fetches before either wins ingestion. Replay uses the current available credentials, so rotation before an eligible attempt can recover it. Exhausted entries have no reset mechanism.
- **FIXED.** Lifecycle operations now expose lifecycle state/version, oldest held reference timestamp, references expiring within 24 hours, exhausted replay count and pending notifications. Unknown-outcome counts are scoped to WhatsNexus. The UI surfaces expiry and exhaustion. Provider pause remains unverified and the last verified health timestamp remains empty until there is independent evidence.

## WhatsNexus independent outbound paths

**PARTIALLY VERIFIED**, from the sibling Whatsnexus backend at source revision `9b91711` and its working tree. Confirm the deployed revision and worker topology before applying any finding to production.

| Origin | Source path and independence |
| --- | --- |
| Campaigns | `app.js` starts scheduling and Redis queues. `campaignDispatchWorker.js` and `campaignSendWorker.js` execute independently and campaign code includes a cron fallback. Campaign status and provider-error pauses apply to campaign work. |
| Scheduled and follow-up messages | `scheduledMessageCron.js` reads due `ScheduledMessages`, then calls `sendWhatsAppTemplate`. The app runs it every minute independently of PulseOS. Appointment service producers populate scheduled rows. |
| Appointment notifications | The same scheduler checks appointment reminder eligibility. `appointment.service.js` also has a direct template send. Appointment flows in `AuthWhatsapp.controller.js` can issue interactive or direct replies. |

| Manual | Messages and AuthWhatsapp controllers call provider send helpers directly for agent-initiated messages, independently of PulseOS. Text, media, templates and interactive sends must be inventoried at actual Meta submission call sites. |
| PulseOS machine dispatch | The integration router exposes authenticated messages, text, media and dispatch lookup operations. Its template dispatch service persists send intent and uses the original external ID as its idempotency key. **BLOCKED.** A single tenant pause covering all seven send origins was not established in the inspected paths. In `pulseos.service.js`, `forwardPulseosInbound` throws on upstream non-2xx. `AuthWhatsapp.controller.js` awaits it before its local dedupe/storage gate and its enclosing catch sends 200. A source comment anticipates Meta retry, but this path acknowledges to Meta on failure. Require the companion team to demonstrate persistence and replay of inbound messages, or an explicit upstream retry response with proven provider retry. Keep that correction independent of the outbound pause protocol.

## Proposed WhatsNexus pause/resume contract

**DEFERRED to the companion team.** Implement and stage this contract in WhatsNexus before PulseOS operators rely on provider-wide pause.

1. Add authenticated commands `POST /pulseos/tenants/{binding}/messaging-pause` and `POST /pulseos/tenants/{binding}/messaging-resume`, plus a read-only status endpoint. Use a scoped management identity restricted to the pre-established PulseOS hospital to WhatsNexus tenant binding. Resolve the local tenant server-side and reject mismatched credentials, tenant or scope. Keep normal dispatch and callback keys separate from pause authority.
2. Require an idempotency key stable across retries, `expectedVersion`, PulseOS lifecycle version and a bounded operational reason. Persist one command result with the tenant state and audit entry. Identical retries return the stored outcome. Same key with different action or parameters and stale version return 409. Store and compare a monotonic fencing generation.
3. Persist `ACTIVE`, `PAUSING` and `PAUSED` with version, effective timestamp, originating command and unresolved admitted-send count. Atomically deny admission when pause starts. Hold a per-tenant durable permit across the final provider submit boundary, or use an equivalent fence that survives separate processes and crashes. A pause reports effective only when old-generation submitters are fenced and outstanding permits have a known completion or an explicit ambiguous disposition. Provider-accepted sends can still deliver.
4. Gate worker claim and last submission for campaigns including the fallback, scheduled/follow-up, appointment direct and scheduled, AI replies, handoff, manual sends and PulseOS dispatch. A stale job must fail the final generation check even if claimed earlier. A bounded response should identify the paused reason before any physical send. Kill/partition a worker in staging to validate the fence and permit recovery.
5. Keep stable IDs, schedule and original eligibility metadata for queued work. Recheck appointment state, deadlines, templates, consent and effective tenant state on resume. Expire stale work by approved policy. Preserve billing reservations, ledger transitions and original message idempotency. A recorded `send_started` or unknown outcome enters reconciliation using its existing dispatch reference and must never be blindly resubmitted.
6. Keep signed callbacks, receipt ingestion, dispatch lookup and billing/outcome reconciliation available during pause. Expose authoritative pause version, effective state and unresolved count to PulseOS without patient content. Audit actor, binding, request ID, old/new state, fence generation, timestamps and outcome.
7. Require a separate explicitly authorized resume command with the current expected provider version and deliberate policy for queued work. On code rollback keep the provider fence active or fence all legacy producers externally before rollback. Preserve dispatch and billing state and prove lookup/callback continuity. Stage each origin in paused and resumed states, plus a concurrent send, timeout after external acceptance, crash, retry, stale version and wrong-tenant command.

## Remaining races and priorities

- **BLOCKED P0.** Companion inbound acknowledged-loss, provider pause, active receipt/dispatch lookup continuity, provider credential compatibility and actual retry or alternate enquiry capture.
- **PARTIALLY VERIFIED P0.** Rolling cutover must fence older API routes, worker replicas and independent schedulers. Summary, call-intelligence and ads work may have already passed preflight and can finish. Browser/worker fixtures do not prove the production topology.
- **PARTIALLY VERIFIED P1.** Authentication/configuration for call and messaging intake is evaluated before admission. Rotation, endpoint reassignment or connector disable racing an authenticated request is a distinct boundary from hospital lifecycle. Stage gateway and operator coordination for rotation. Different event IDs for the same contact can compete over conversation/Journey creation according to existing identity constraints. Historical partially processed records require review before bulk replay.
- **PARTIALLY VERIFIED P1.** Website domain ingestion and journal completion remain separate commits. If a completion write fails after domain commit, the request reports a failure and later recovery depends on submission ID dedupe. An in-progress duplicate returns a temporary refusal. Before replaying older failed journals, check actual domain effects.
- **DEFERRED P1.** Call integration publishing remains the existing in-process post-commit mechanism. A crash after call commit can lose the integration fact. Delivery-status callbacks that arrive before a message can be matched can require provider-side reconciliation. Track any correlation gaps in staging.
