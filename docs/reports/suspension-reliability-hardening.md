Website intake returns a synchronous response to the submitting site. Provider payload callbacks use HTTP success as the intake acknowledgement. Whether a provider retries a failed response, for how long and whether its event is exportable must be verified per integration. Delivery receipts can continue during suspension and use the connector journal to suppress duplicates. Outbound webhooks expect receiver success and use a stable external event ID across delivery attempts. Notification, summary, call-intelligence, ads and maintenance ticks have no inbound callback to acknowledge.

The companion repository's PulseOS machine router defines pairing, health, templates, message/text/media dispatch, and lookup by dispatch ID. The operations router defines integration management, key rotation, dispatch resolution and callback replay. Neither inspected router exposes an authenticated tenant-wide pause that proves campaigns, scheduled sends, follow-ups and AI replies all stop. A connector readiness status does not establish that autonomous work stopped.

## Implemented controls

- Migration 0053 adds the tenant-scoped suspended Meta reference table, a connector/lead primary key, tenant and expiry indexes, and a seven-day retention window. Each request is limited to 256 KiB and 50 references. The holding limit is 1,000 unexpired entries per tenant, including processed markers. Holding accepts only bounded provider identifiers and a timestamp. Authentication, exact connector ownership, and live Meta Page binding are checked before durable acceptance. The retention job removes up to 500 expired rows per tick and skips locked rows.
- Set the existing connector configuration field `leadPageId` to the authorized Meta Page ID before routing live events to this version. A missing or mismatched live binding returns 503. Fixture connectors can omit the binding for existing tests. A matched platform callback retains the same connector throughout. Meta fetches use a ten-second request timeout. Reference expiry does not guarantee the provider will still return the original lead.
- `GET /platform/hospitals/:id/lifecycle-operations` requires lifecycle read permission. It returns counts, oldest queued creation time, and coordination or reconciliation indicators. A verified health timestamp is unavailable because the existing connector timestamps also represent ordinary events and syncs. The interface reports that absence explicitly.
- `POST /platform/hospitals/:id/replay-held-meta-leads` requires the browser Super Admin restoration permission, explicit approval, an active hospital and the current lifecycle version. Both endpoints preserve legacy versus onboarding ID routing. Replay handles at most five references, at most three attempts per reference, and one- then two-minute failure backoffs before the final attempt. Each item uses its original connector and current credential row. Connector disablement, missing credentials or a changed Page binding prevents ingestion. A database savepoint keeps the ingest and event claim atomic. The batch and item outcomes are audited without payloads or provider identifiers. There is no automatic replay at restoration.
- Suspended payload-bearing callbacks now return 503 after authentication instead of emitting an intake success response. A mixed Meta WhatsApp batch still applies eligible delivery receipts before returning 503. Disabled connectors retain the preceding disabled-connector behavior. No storage policy was inferred for call recordings, raw message bodies, full Google forms, or provider attachments.
- A 503 records refusal at the HTTP boundary. That response alone gives PulseOS no copy of the enquiry. The Runo, CCS and Meta WhatsApp active handlers can also return success after writing a failed journal entry. Recovery for those failures depends on redelivery or an approved source-side export. The hold and replay API covers Meta Lead Ads references only.
- Website writes hold a tenant row lock for the actual ingestion and return 503 when suspension wins. Meta admits or holds under the same tenant lock used by suspension. PulseOS notification submissions, conversation text/media, outbound webhook submissions and test sends use shared tenant locks through provider submission. Outbound webhook enqueue and lifecycle transition are ordered by the same locks. Previously admitted submissions can finish and cannot be recalled. Provider status reconciliation and unknown WhatsNexus outcomes retain their existing references and no-resend policy.
- Each Meta lead reference commits independently. A rejected or temporarily unavailable reference makes the batch response 503. Later admissible references are still accepted and deduplicated on redelivery. Graph fetch failures report only the HTTP status.
- Google lead ingestion and its completion marker commit together under a shared tenant lock. A savepoint rolls back partial writes on processing failure and preserves a retryable failure marker with a fixed error code.
- Runo and CCS callbacks use connectors for their exact provider. CCS rejects missing, malformed and nonmatching credentials. The connector journal retains an event type marker, and call metadata excludes the accepted credential fields.
- Hospital session issuance takes a shared tenant lock. Suspension takes an exclusive lock and revokes tenant sessions in the same transaction. Concurrent lifecycle changes serialize on the tenant and compare the submitted lifecycle version.
- Overdue pending reminders are suppressed at restoration. Eligible future reminders follow normal send-time rules for appointment state, capability, rule, template and connector. Previously accepted or ambiguous sends retain their dispatch history for reconciliation. Outbound webhook retry IDs remain stable, and ads sync retains its existing date-range logic. Meta replay requires operator approval. Other payload-bearing paths depend on provider redelivery or an approved alternate capture procedure. Runo, CCS, Meta WhatsApp and WhatsNexus inbound still have a gap between checking lifecycle and writing domain records. Summary, call intelligence and ads jobs still rely on their existing lifecycle checks.

## Proposed WhatsNexus-side contract

A separately authorized change in WhatsNexus should expose a tenant-bound, independently authorized and audited pause/resume command with an expected version and stable request ID. It should report the effective paused state, queue and in-flight counts, actor and time, and enforce that shared state at every autonomous scheduler and provider submission boundary. Keep status callbacks and lookup available. Require a separately approved resume and preserve accepted or ambiguous dispatch references. Integration disablement, callback status and key rotation alone do not prove autonomous work is paused. The external repository was inspected read-only.

## Rollout and rollback

1. With production approval, back up schema and retention controls, inventory scheduled jobs/workers, configure live Meta Page bindings and verify least-privilege connector access. Agree with each payload-bearing provider on retry windows, alternate capture/export and retention handling. Verify pilot data availability before enabling replay.
2. Apply 0053 before starting the new API or worker. Fence intake and dispatch while draining old instances and independent schedulers. Keep the status callback routes running on a version that preserves receipt handling. Provision expiry cleanup and alert on held references approaching expiry.
3. Start the new API fleet, then workers, and verify gateway routing only reaches lifecycle-capable instances. Stage the independently authorized WhatsNexus-side pause before representing provider-side suspension as complete. Verify exact site fallback for website 503 and provider retries or export on every source.
4. On rollback, retain 0052/0053, audit history, held references, disabled login flags, revoked sessions and unresolved dispatch keys. Close or route affected intake to a verified fallback and stop old worker egress before reverting. Preserve read-only status reconciliation. Never send an ambiguous dispatch again solely because a deployment rolled back.

- The final regression run passed 268 tests across 21 Vitest files. It covered onboarding, tenant login, patient and journey workflows, appointments, notifications and reconciliation, provider fixtures, integration delivery, ads, calls and conversation summaries. The earlier 42-test focused run overlaps this total. The dedicated six-test platform suite ran separately.
- Focused Vitest run passed 42 tests across five suites. It included the mixed Meta batch, signature rejection, replay bounds and tenant isolation, deleted credentials, the Google lead waiting on a real PostgreSQL lifecycle lock and duplicate redelivery, and CCS credential handling.
- The dedicated platform suite passed all six tests against a separate clean PostgreSQL database. It exercised browser session authorization, concurrent lifecycle commands, signed delivery receipts during suspension, blocked website intake, expired-notification suppression and fresh staff login after restoration.
- Playwright passed four mocked browser scenarios on rerun and one real MFA enrollment and sign-out scenario against a local API and synthetic database. The form fixture now fills and verifies the hospital name after the other fields. An earlier run lost the first field during navigation.
- Web TypeScript, full lint and production build passed using an explicitly loopback API origin. The API and browser provider fixtures are local simulations. No staging provider was contacted.
- API TypeScript, build and full lint passed. Lint reported three unused-symbol warnings in platform authentication and the ophthalmology demo seed. `git diff --check` passed.

## Production blockers and staging checks

1. **P0 — WhatsNexus autonomous sends.** Verify an authorized pause and separate resume against scheduled messages, campaigns, follow-up automations and AI replies. Verify that status callbacks and ambiguous-dispatch lookup remain available during the pause. Reconcile submissions already accepted before declaring provider suspension effective.
2. **P0 — Patient enquiry capture.** Verify Runo, CCS, Meta WhatsApp, WhatsNexus and Google Lead Forms handling of 503, actual retry horizons and an approved alternate capture or export path. Verify the user-visible website fallback. A failed delivery can still become a lost enquiry. Test live signed Meta Lead Ads deliveries against an authorized Page and verify later Graph retrieval within the configured retention window, including credential revocation and Page reassignment.
3. **P0 — Cutover and remaining admission gaps.** Fence every previous API and worker, including jobs embedded in `server.ts` and separately scheduled copies. For Runo, CCS and both WhatsApp inbound paths, quiesce already-admitted requests or introduce transactional admission before relying on suspension as a hard cutoff. Drain or reconcile in-flight summary, call-intelligence and ads jobs. Confirm gateway routing for acquisition and receipt routes after switching the API fleet.
4. **P1 — Staging dispatch and backlog.** Verify provider delivery signatures, receipt processing during suspension, ambiguous-outcome lookup without resend, webhook receiver deduplication, future versus expired or cancelled reminders, replay limits, expiry cleanup and provider health evidence. Approve retention and define escalation for lead references that expire or exhaust retries.
5. **P0 — CCS authentication and historical records.** Before switching a live CCS route, prove that its callback supplies one of the supported tenant credentials and that its call ID survives redelivery. If keys have been sent in query strings or bodies, use the authorized connector-key rotation process and review historical gateway logs, event journals and call metadata for retention or cleanup.
